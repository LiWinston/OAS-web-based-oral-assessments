# US 6.7 – Course Admin Reporting User Flow Context

## User Story & High-Level Expectations
- **User Story 6.7** (Epic 6 – Mark Management & Publication): administrators need specialized reports covering scheduling overview (slots, venues, examiners, validity, bookings), mark results (examiner-specific marks, aggregation options, comments), and examiner marking trends (real-time averages) to monitor the assessment process end-to-end.【Docs/Requirement/user_stories.md:111-121】
- The PRD establishes three dedicated report surfaces for Course Admins—Scheduling Overview, Mark Results, and Examiner Trends—each expected to expose exportable data and highlight staffing or scoring issues.【Docs/Requirement/Product Requirements Document.md:160-174】
- PRD scope explicitly excludes advanced analytics/AI beyond these reports; anything deeper than the specified insights is out of scope for this phase.【Docs/Requirement/Product Requirements Document.md:232-238】

## Adjacent User Flows & Dependencies
- **Course Admin Results Moderation Flow** defines the current post-marking workflow: per-assessment review, manual final score overrides, and release actions; reports must align with the submissionId/sessionId model and status transitions (`DRAFT → SUBMITTED → REOPENED/RELEASED`).【Docs/Design/CourseAdmin-Marks-Consolidation-and-Release-UserFlow.md:1-107】
- **Examiner Marking Flow** underpins the data the reports surface—each examiner works against assignment rubrics, can save drafts, submit, or be reopened by an admin. Reports need to respect rubric structures and per-criterion data captured here.【Docs/Design/Examiner-Assessment-Flow.md:1-88】
- **Examiner Marking History** UX limits examiner visibility to their own marks and versions (no cross-examiner analytics). Reporting that compares examiners therefore sits firmly in the admin domain, and should aggregate data without exposing per-examiner breakdown back to examiners.【Docs/Design/Examiner-MarkingHistory-UserFlow.md:1-108】
- **Student Results Release** depends on at least one examiner submitting; the release status (`RELEASED`/`NOT_RELEASED`) controls student visibility but, per current product expectation, reopening an examiner’s assessment does **not** automatically flip the release flag back to `NOT_RELEASED`. Reporting should still surface where release hasn’t yet occurred and where reopened assessments co-exist with released results.【Docs/Design/CourseAdmin-Marks-Consolidation-and-Release-UserFlow.md:51-88】
- **Scheduling & Session Management**: Admins configure sessions (date/time/venue/examiner requirements) through the timeslot management UI and `courseAdminSessionService`. Reports drawing a scheduling overview must combine session configuration, examiner assignment, and booking data exposed by `/api/admin/sessions/assignments/{assignmentId}` and related endpoints.【frontend/app/admin/courses/[courseId]/assignments/[assignmentId]/timeslots/page.jsx:1-160】【frontend/services/courseAdminSessionService.js:10-200】

## Current Frontend Landscape
- **Results Hub ( `/admin/results` )** is the current entry point for administrators to monitor assignments. It loads all courses the admin owns, allows course switching, and shows per-assignment readiness chips (rubric, sessions, results) plus quick metrics (total assessments, released, pending, average score) calculated via `useAssignmentResultsSummary`. This hub is UI-only and depends on the same admin results endpoints intended for the future reports.【frontend/app/admin/results/page.jsx:1-254】【frontend/components/admin/results/ResultsHubAssignmentRow.jsx:1-179】【frontend/hooks/admin/useAssignmentResultsSummary.js:1-119】
- **Assignment Results List** (`/admin/courses/{courseId}/assignments/{assignmentId}/results`) already renders a paginated table with filters (search, release status), average/effective scores, and manual override badges. It relies on `useAssessmentList` → `adminResultsService.listAssessments` which currently defaults to mock data unless `NEXT_PUBLIC_USE_MOCK_API` is set to `false`.【frontend/app/admin/courses/[courseId]/assignments/[assignmentId]/results/page.jsx:1-200】【frontend/services/adminResultsService.js:407-474】
- **Assessment Detail View** surfaces examiner-level panels, override controls, review dialog, and release dialog. It reuses the examiner RubricTable through `RubricSnapshot` to present rubric selections and comments. Any reporting system must reuse or extend these components/data structures to avoid duplication.【frontend/app/admin/courses/[courseId]/assignments/[assignmentId]/results/[submissionId]/page.jsx:153-296】【frontend/components/admin/results/ExaminerPanel.jsx:1-74】【frontend/components/admin/results/ScoreSummaryPanel.jsx:1-54】
- **Feature Flags**: `adminResultsService` and downstream hooks honour a mock/real toggle. Without setting `NEXT_PUBLIC_USE_MOCK_API=false`, all reporting data comes from an in-memory dataset, so integration with Spring Boot requires flipping that flag and ensuring backend endpoints meet the expected response contract.【frontend/services/adminResultsService.js:413-471】
- **README Status** explicitly marks Reporting & Analytics as “Not Started”; existing UI only covers moderation, not the PRD-required analytical views (scheduling overview, mark aggregation comparison, examiner trends).【frontend/README.md:757-767】

## Backend APIs & Behaviour
- **Admin Results Controller** exposes list, detail, review, final score override, and release endpoints under `/api/admin/subjects/{subjectId}/assignments/{assignmentId}`. Reports must consume these endpoints (or extensions thereof) for the mark-results dimension; filtering by sessionId and release state is already supported server-side.【backend/src/main/java/org/swen90017/oas/controller/AdminResultsController.java:31-159】
- **Service Implementation** computes averages across submitted examiners, applies manual overrides, and enforces “at least one submitted examiner” before release. The current Spring service resets release status to `NOT_RELEASED` when an examiner is reopened, but the clarified requirement is that release status should remain unchanged in that scenario—highlighting a behaviour gap to resolve when designing reporting logic. Manual overrides currently update *all* examiner submissions for the student across sessions within the assignment, which impacts how aggregated figures should be interpreted in reports.【backend/src/main/java/org/swen90017/oas/service/impl/AdminResultsServiceImpl.java:49-200】【backend/src/main/java/org/swen90017/oas/service/impl/AdminResultsServiceImpl.java:129-188】
- **Session Management APIs** (under `/api/admin/sessions/assignments/{assignmentId}` and related routes) provide the session, venue, examiner assignment, and publish status data needed to build the scheduling overview (e.g., staffed vs required examiners, booking counts).【frontend/services/courseAdminSessionService.js:10-200】
- **Student Results APIs** use conditional GETs and serve released results, rubric breakdowns, and examiner feedback. Because student visibility depends on final release states, any reporting on release readiness should correlate admin-side release data with what students can see via `/api/students/{id}/assignments/{assignmentId}/result` endpoints.【frontend/services/studentResultsService.js:20-144】

## Data Relationships & Flow Considerations
- A single assessment is keyed by `(assignmentId, sessionId, submissionId, entityId)` with entity kind (`GROUP` or `INDIVIDUAL`). Reports must aggregate across these keys (e.g., by session for scheduling, by student/group for mark results, by examiner for trends).【Docs/Design/CourseAdmin-Marks-Consolidation-and-Release-UserFlow.md:39-74】
- Examiner trend reporting requires summarising `examinerScorePct1dp`, submission statuses, and timelines; the data currently exposed in detail view (`adminResultsService.getAssessmentDetail`) already contains per-examiner totals, comments, and status history, but no aggregated API exists yet. A new backend aggregation endpoint may be necessary if frontend aggregation proves expensive for large datasets.【frontend/components/admin/results/ExaminerPanel.jsx:27-59】【backend/src/main/java/org/swen90017/oas/service/impl/AdminResultsServiceImpl.java:49-188】
- Scheduling overview needs to reconcile session definitions, examiner assignments, and booking state. The timeslot UI fetches sessions per day and maintains examiner a/b assignments via `courseAdminSessionService`, but there is no consolidated “validity” computation yet (e.g., mismatched required vs assigned examiners). Reports will likely need additional backend joins or client-side rules using the same services the configuration UI consumes.【frontend/app/admin/courses/[courseId]/assignments/[assignmentId]/timeslots/page.jsx:1-160】【frontend/services/courseAdminSessionService.js:31-200】

## Known Gaps & Open Questions
1. **Dedicated reporting endpoints** for scheduling overview, mark aggregation comparisons, and examiner trends do not yet exist; current services deliver per-assessment data only. Do we extend existing endpoints or add summaries (e.g., `/reports/scheduling`, `/reports/examiner-trends`)?
2. **Validity definition for scheduling** (what counts as “invalid” slot) isn’t codified in docs—clarification needed on rules (e.g., no examiner assigned, clashes, capacity overbooked).
3. **Aggregation options**: PRD references selectable aggregation methods (e.g., average). Current user flow spec intentionally removes aggregation choice (default=average). Should reports reintroduce configurable aggregation, or simply surface current computed averages with manual override indicators?
4. **Examiner trend time granularity**: “Real-time averages” imply live updates—confirm whether trend reports should show overall averages, per-criterion charts, or time-series (e.g., per day/week).
5. **Export requirements**: PRD mandates exports; file format (CSV vs PDF) and scope (per report vs combined) remain unspecified.
6. **Mock vs real data**: With mocks enabled by default, QA/UX validation may differ from production data (e.g., mock dataset already includes overridden & reopened examples). Confirm environment plan for integration testing.
7. **Release-on-review behaviour**: Backend currently flips release status to `NOT_RELEASED` whenever an examiner is reopened, conflicting with the clarified expectation that release visibility should persist. Decide whether to amend backend behaviour or surface the distinction explicitly in reports.
8. **Performance**: `useAssignmentResultsSummary` fetches all assessment pages (page size 200) per assignment to compute metrics client-side. For large cohorts this is expensive; may need backend summarisation before scaling the report UI.【frontend/hooks/admin/useAssignmentResultsSummary.js:41-105】
