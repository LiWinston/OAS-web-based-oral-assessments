# Oral Assessment System (OAS) – Product Requirements Document

## Overview

The Oral Assessment System (OAS) is a web-based platform for universities to conduct oral examinations efficiently. It addresses the current manual, time-consuming process of scheduling oral exams, coordinating examiners, and collecting results 1. OAS streamlines these tasks by providing integrated tools for user management, assessment configuration, scheduling and booking, assessment execution, mark aggregation, and result dissemination 1. The platform integrates with the Canvas Learning Management System via CSV import/export and includes basic email notifications to keep users informed 1. Overall, OAS aims to improve the user experience for administrators, examiners, and students by centralizing the oral exam workflow in a single, easy-to-use interface.

## Goals

- **Streamline Oral Exam Process**: Eliminate inefficient manual steps in organizing oral assessments. Automate scheduling, booking, and marking workflows to save administrative time.
- **Enhance Fairness & Consistency**: Ensure each student is assessed under uniform conditions. Support standardized rubrics and multiple examiners per session to improve grading consistency.
- **Improve User Experience**: Provide an intuitive, modern web interface for all user roles (admins, examiners, students) to easily perform their tasks. Minimize complexity with clear navigation and guidance through each step.
- **Seamless Integration**: Safely integrate with existing systems by importing student/course data and exporting results to Canvas LMS via CSV 1, avoiding duplicate data entry.

## Personas

OAS serves several key user personas, each with specific needs and interactions:

- **Super Admin (Institution-level Administrator)**: Oversees the system at a high level. This persona approves and manages Course Admin accounts and can view a read-only list of all courses in the system. Super Admins ensure the right people have access but do not configure course details unless they also act as a Course Admin for a course.
- **Course Admin (Subject Coordinator)**: Typically a faculty member or course coordinator who sets up and manages an oral assessment for their course. Course Admins create courses and assignments, upload student/group data, define rubrics, set up time slots, assign examiners, and oversee the assessment process for their course. They control when results are released and handle exporting grades to the LMS.
- **Examiner**: Academic staff or tutors who conduct the oral exams and grade students. Examiners review the assessments they're assigned to, self-assign to specific time slots, then use the system's marking interface to record scores and feedback during exams. They can add notes and contribute to shared feedback comments. Their focus is on the assessment execution phase.
- **Student**: The examinee - a student enrolled in a course with an oral assessment. Students use OAS to book their oral exam slot (for individual or group assessments), receive confirmation and reminders, and later view their results and feedback once released. Students only have access to their own assessment information and cannot see others' results. (First-time student users must also complete a simple account setup and agree to any required privacy policy upon registration.)

## Functional Requirements

The OAS platform will provide the following functional capabilities (aligned with project scope must-haves):

- **User Account Management**: Secure account creation and login for students, examiners, and admins. The system must support role-based access control (different views/permissions per role) and password or email-based authentication. New user onboarding is streamlined via email invitations for first-time users to set up their password. Super Admins can approve or revoke Course Admin access as needed.
- **Course & Assignment Configuration**: Ability for Course Admins to set up academic terms, create courses/subjects, and create assignments within each course. For each assignment, the admin can specify the assessment type - Individual, Group, or Mixed (mixed includes both group and individual components). The system provides a form or wizard to input assignment details and define the structure of the assessment.
- **Rubric and Feedback Customization**: A flexible rubric builder for Course Admins to define assessment criteria and scoring. Admins can create a hierarchy of criteria/sub-criteria and set customizable performance levels for each criterion (varying number of levels, custom level names, and manual point values). The rubric builder also allows defining predefined feedback comments per criterion, which examiners can select during marking. Examiners should be able to add new comments to the comment library on-the-fly during marking for reuse by others. These features ensure feedback is consistent yet adaptable to each criterion's needs.
- **Student/Group Data Import**: Course Admins can import a CSV list of students (and group memberships) for each assignment. This populates the list of participants eligible to book slots. Uploading data is done at the assignment level (not course-wide) as required by the client. The system validates CSV format and content, providing clear error messages if there are issues. Admins may re-upload an updated CSV during the semester to reflect changes (e.g. student withdrawals or group changes), with an option to preview changes before overwriting.
- **Scheduling & Time Slot Management**: A comprehensive scheduling module for oral exams. Course Admins define specific time slots for the assessment including date, start and end time (or duration), and venue/location. They also specify how many examiners are required per slot and how many student groups or sessions can be accommodated in that slot (for example, a one-hour slot might fit multiple 15-minute sessions). The system supports parallel slots (concurrent sessions in different venues or with different examiner teams) and must visually distinguish overlapping slots clearly. Students see only slots that have sufficient examiners assigned (validated slots) and that are not full. The platform must allow students (or one member of a group) to book a slot from the available options, and prevent double-booking or overbooking of slots. Course Admins can enable or disable student self-rescheduling; if enabled, students may reschedule their booking within defined deadlines.
- **Examiner Self-Assignment**: Examiners can log in and view the available time slots that need examiners for a given assignment. They can self-assign to specific slots of their choosing, up to a limit set by the Course Admin (e.g. an examiner might only be allowed to examine, say, 5 sessions in total). Once an examiner has assigned themselves, that slot's examiner count is updated. The system should prevent examiners from joining more slots once they've reached the limit of sessions set by the admin. (If examiner assignment is incomplete for any slot, admins are alerted so they can recruit additional examiners or adjust the schedule.)
- **Notifications**: An email notification system to keep everyone informed. The system sends out booking confirmations to students upon booking a slot, as well as reminder emails to students and examiners before their scheduled exam time. It also emails newly added users (e.g. when a Course Admin adds an examiner or student to a course, or when a Super Admin creates a Course Admin account) with appropriate onboarding links. All emails should use institution branding and clear language. (Real-time in-app notifications may be minimal, as email is the primary channel, but the UI should indicate status like "booking confirmed" after an action.)
- **Assessment Execution (Examiner Interface)**: An intuitive marking interface for examiners during the oral exam. Examiners can pull up the scheduled session (student or group) they are examining and see that assignment's rubric on screen. For each criterion, the examiner selects the performance level achieved (or enters a score) and can choose from predefined comments or write new comments. The interface should allow examiners to add additional comments into the shared pool if something unique comes up (making it instantly available for other examiners marking the same assignment). Examiners can also enter overall feedback text if needed. A "Notes" field is provided for examiners' private notes or observations; notably, these notes will be visible to the Course Admin for oversight purposes (as requested by the client, the previously named "Private Note" is now shared with admins). The examiner should be able to save a draft of their marks/feedback if the assessment is in progress or if they need to pause, and later come back to finalize. Once they are satisfied, they submit the final marks which locks in the scores for that session.
- **Mark Calculation & Aggregation**: For each assessed session, if multiple examiners evaluated the same student/group, the system can aggregate marks according to rules. Course Admins can configure the aggregation method (e.g., average of examiners' scores, or take maximum/minimum) for the final mark if multiple examiners are used. The system will compute the final results based on this method. In a mixed assignment (having individual and group components), the platform will combine group marks and individual marks appropriately to produce each student's overall score.
- **Reporting and Analytics**: Course Admins have access to several reports to monitor and review the assessment process. Required reports include:
  1.  A Scheduling Overview report showing all time slots, their venues, which examiners are assigned, which student/group is booked in each, and whether slots have the required examiners (valid/invalid status).
  2.  A Mark Results & Aggregation report showing detailed breakdown of marks each examiner gave per criterion, all comments given, and the final aggregated mark per student/group.
  3.  An Examiner Trends report showing, for each examiner, the average marks they have given across all sessions (to help identify if an examiner is an outlier in scoring).
      These reports should be viewable in the admin UI and exportable (e.g. CSV or PDF) for record-keeping.
- **Results Release Control**: The system allows Course Admins to control when students can see their results. By default, students cannot view marks/feedback until the Course Admin releases the results. Admins can review all marks, make any manual adjustments if needed, then trigger a "release results" action which notifies students that their feedback is available. Students then can log in and see their performance and comments.
- **Canvas LMS Integration**: To avoid double data entry in the University's official systems, OAS supports simple LMS integration via file exchange. Admins can import student enrollment data from Canvas by uploading standardized CSV files (as mentioned above). After assessments, Course Admins can export grades and feedback in a Canvas-compatible CSV format ready for upload to the LMS gradebook. This export includes each student's final mark and possibly key feedback comments. The interface should guide the admin to ensure the data matches Canvas requirements (e.g. correct columns) and confirm success of the export.
- **Security & Compliance**: The platform must enforce secure access and protect personal data. All user interactions require authentication (with support for secure password rules or email verification login). New users registering must agree to the university's privacy policy (displayed on first login). The system will maintain an audit log of important actions (like account creations, data imports, grade submissions) for accountability. Additionally, it should adhere to accessibility standards (WCAG) so that all users, including those with disabilities, can use the system.

## User Flows

Below are the primary user workflows for each persona, illustrating how users will navigate the OAS interface to accomplish key tasks. Each flow is described step-by-step, and critical screens or decision points are highlighted. (Visual flow diagrams are provided where appropriate to complement the text.)

### Super Admin Flow

**Goal**: Approve new Course Admins and get an overview of all courses.
**Context**: Performed by an institutional Super Admin infrequently (e.g., at semester start).

1.  **Log In**: Super Admin logs into OAS using their credentials (as a Super Admin user).
2.  **Add Course Coordinator/Admin**: The Super Admin add a Course/Subject Coordinator and grants access with a click (the system might send an email to the new Course Admin upon approval). They can also add new Course Admin accounts manually if needed.
3.  **View System Overview**: The Super Admin can navigate to an "All Courses" overview page. Here they see a list of all courses/subjects in the system and the corresponding Course Admin (coordinator) for each. This view is read-only - they cannot edit course details but can use it to monitor which courses are using OAS.
4.  **Log Out**: After performing administrative duties, the Super Admin logs out. (There are otherwise no complex multi-step interactions for this role beyond user management.)

### Course Admin Flow

**Goal**: Configure an oral assessment for a course from start to finish.
**Context**: Performed by a Subject Coordinator or Course Admin preparing an upcoming oral exam (e.g., at the beginning of the term, and updating as needed).

1.  **Log In & Select Course**: The Course Admin logs into OAS and lands on their dashboard. They see a list of courses they manage (or an option to create a new course). They select an existing course or create a new one if this is the first time using OAS for that subject.
2.  **Create Assignment**: On the course page, the Course Admin clicks "Create New Assessment" (assignment). They enter details such as the assignment name, description, and select the type (Individual / Group / Mixed). For a Mixed type, the interface may prompt for additional setup (like which criteria are group vs individual).
3.  **Import Students/Groups**: The Course Admin navigates to the "Participants" step for the assignment. They upload the CSV file containing the list of students and group memberships for this assignment. The system validates the file and shows a preview of the data to be imported. The admin confirms to import, and the assignment now has its roster of participants. (If changes occur later, the admin can return to this step to re-upload an updated CSV, with a change preview and merge feature.)
4.  **Define Rubric**: Next, the Course Admin configures the marking rubric for the assignment. Using the rubric builder UI, they add multiple criteria (and sub-criteria if needed). For each criterion, they set the total points and define performance levels. The admin can add as many performance levels as needed (e.g., "Excellent", "Good", "Pass", "Fail"), edit the name of each level, and assign a specific point value to each. The interface enforces that the sum or maximum of level points aligns with the criterion's total points (with validation for any errors). The admin also enters predefined feedback comments for each criterion - for example, common phrases describing strong or weak performance on that criterion. If the rubric builder UI becomes complex, the system may use a multi-step form or modals for adding levels and comments to keep it manageable. Once the rubric is defined, the Course Admin saves it.
5.  **Configure Time Slots**: The Course Admin switches to the "Scheduling" step. Here they create the specific time slots for the oral exams. For example, the admin can click "Add Time Slot" and input: Date, Start Time, End Time (or duration), Venue, and number of examiners required. They can create numerous slots back-to-back or in parallel as needed (e.g., three parallel slots at 10:00 AM in different rooms). For each slot, they also specify how many separate student sessions it can hold. (In many cases, one slot = one session, but if a slot is long, they might allow multiple sequential sessions in that one slot.) The UI might display a calendar view or tabular list of slots. The Course Admin adds all the slots covering the period of the assessments. The system should highlight if any slot is incomplete (for example, missing an examiner assignment or overlapping incorrectly).
6.  **Assign Examiners to Course**: The Course Admin navigates to the "Examiners" management for the course/assignment. They ensure all examiners who will participate are added to the system (either by inviting them via email or selecting existing accounts). The admin can set a limit on the number of sessions each examiner should examine for this assignment. For instance, they might limit each examiner to 5 sessions total for fairness. Once examiners are added, the admin notifies them (the system may send an email invite) that they can sign up for specific slots.
7.  **Monitor Examiner Sign-ups**: After configuring slots, the Course Admin monitors examiner self-assignments. In real-time, they can see in the scheduling overview how many examiners have signed up per slot. If some slots do not have enough examiners (e.g., a slot requires 2 examiners but only 1 has joined), that slot might be marked "invalid" or highlighted. The Course Admin can prompt additional examiners to sign up or adjust slot requirements. This monitoring might be done via the Scheduling Overview report which shows slot status and assigned examiners.
8.  **Student Booking Opens**: Once enough slots and examiners are in place (or a certain date is reached), the Course Admin opens the schedule for student bookings. They may communicate to students (outside the system or via a system notification) that they can now book their assessment slot. Students will only see slots that have the required number of examiners (valid slots) and that are not already fully booked.
9.  **Oversee Bookings**: As students begin to book slots, the Course Admin can view who has booked which slot (e.g., via the Scheduling Overview or a list of bookings). If the system allows, the admin can manually move bookings or book students into slots as well (for instance, to accommodate special cases or assign students who haven't self-booked by the deadline).
10. **During Assessments**: On the day of assessments, the Course Admin may use the system to track progress. They can see which sessions are in progress or completed. They can also view the Marking Results report as examiners submit marks to ensure everyone has entered data.
11. **Review & Release Results**: After all oral exams are conducted, the Course Admin reviews the collected results. They check the aggregated scores and feedback comments for each student/group. If everything looks correct, the Course Admin triggers "Release Results" for the assignment. The system might ask for confirmation and then send out an email notification to students that their results are now available. Students can then view their own marks and feedback. The Course Admin can also download the CSV export of results at this stage to upload into Canvas LMS if needed.
12. **Post-Assessment Cleanup**: Optionally, the Course Admin might revoke examiner access or remove any user who no longer needs access to the course after completion. They ensure data is properly saved and logged out. Future improvements or next-term usage can build on this setup.

_(The Course Admin flow above encompasses all major configuration activities. It is typically a linear progression for initial setup, but the admin can return to earlier steps - e.g. add a slot or adjust the rubric - if needed before the assessment takes place.)_

### Examiner Flow

**Goal**: Sign up for exam sessions and conduct the assessments by grading students.
**Context**: Performed by an Examiner (e.g., instructor or TA) during the scheduling and execution phase of an assessment.

1.  **Log In**: The Examiner logs into the OAS platform with their account. They have been added to one or more courses as an examiner.
2.  **View Assigned Courses/Assessments**: Upon login, the Examiner's dashboard lists the courses or specific assignments for which they are an examiner (e.g., "Course: Data Structures - Oral Exam 1"). The Examiner selects the relevant assessment to manage their participation.
3.  **Browse Available Time Slots**: In the context of that assessment, the Examiner enters a "Time Slots" or "Schedule" section. Here the system displays all the time slots defined by the Course Admin, along with details: date/time, venue, number of examiners required, and how many have signed up so far. The Examiner sees which slots still need examiners (e.g., a slot might show "1 of 2 examiners filled"). They can filter slots by date or other criteria to find convenient times.
4.  **Self-Assign to Slots**: The Examiner chooses which specific slots to cover. For each desired slot, they click "Assign Myself" (or similar) to volunteer for that slot. The system immediately updates the slot's status (e.g., "2 of 2 examiners filled" once they join). Business rules: an examiner cannot exceed the session limit set by the admin - if they try to take too many sessions, the system will prevent it or warn them once they've hit their max. Examiners can also withdraw from a slot before it's locked (up until a certain cutoff time) if their availability changes.
5.  **View Personal Schedule**: The Examiner can navigate to "My Schedule," which shows all the slots (with times and locations) they have committed to. This acts as their personal timetable for the exam day(s). It's important that this view is clear and printable, since examiners may use it to plan their day.
6.  **Prepare for Sessions**: Before the exam sessions, the Examiner might click on each upcoming session in their schedule to view details: the student or group assigned to that session (once students have booked), any specific instructions from the Course Admin, and a link to open the marking interface for that session.
7.  **Open Marking Interface**: When it's time for an exam session to start (or after finishing the live exam), the Examiner opens the marking interface for the scheduled student/group. This interface presents the rubric and input fields for feedback. The Examiner sees the student's name (or group identifier) and the list of rubric criteria. For group exams with individual components, the interface allows toggling between each student in the group for individual scores - possibly via a dropdown or tabs for each student, or by listing all individuals sequentially if that design is chosen.
8.  **Record Marks & Feedback**: During or immediately after the oral exam, the Examiner selects the appropriate level achieved for each criterion on the rubric (or enters a numeric score). They then add comments: the interface lets them choose from the predefined comments (entered by the Course Admin) for each criterion via a dropdown or autocomplete, and/or write custom comments in a text box. If the Examiner writes a new comment that they think would be useful for others, they have an option to add it to the shared library for that criterion so other examiners can use it. They also fill any overall feedback or general comments section for the student if provided. Additionally, the Examiner can write in the "Notes" field any observations or issues (these notes are internal and visible to the Course Admin, not the student, e.g. "Student needed prompting for answer #3").
9.  **Save Draft**: If an Examiner is interrupted or wants to double-check something later, they can save their progress. For example, after an exam, they might save a draft and revisit it later in the day to finalize comments. The system clearly indicates which sessions have saved drafts versus which are submitted.
10. **Submit Marks**: Once the Examiner is satisfied with the scoring and feedback for the session, they submit the results. Upon submission, the data becomes read-only for that session (unless an admin re-opens it) and is counted as completed. The Examiner's submission might trigger an update in the Mark Results report for the Course Admin to see.
11. **Repeat for All Sessions**: The Examiner repeats steps 7-10 for each of their scheduled sessions. The UI should make it easy to jump to the next student/group to mark, especially if exams are running back-to-back. Possibly a "Next Session" button or a return to schedule overview helps streamline this.
12. **Review Past Results**: After all sessions, the Examiner can review what they submitted (for instance, to discuss with course staff). They might access a summary of their own marks given - the system could provide an "Examiner Summary" where they see each student they marked and the final outcome. This can help examiners reflect on consistency of their grading. Additionally, if enabled, the Examiner might see the Examiner Marking Trends info for themselves (how their average compares to others) to self-evaluate, although this is more for the admin; examiners might not commonly see others' data.
13. **Log Out**: When finished, the Examiner logs out. They may later log back in once results are released if they want to see the overall outcomes, but examiners typically are done after marking.

_(Throughout the Examiner flow, the emphasis is on ease of use and minimizing clicks during the marking process. For example, keyboard shortcuts or quick selection for rubric levels can speed up data entry. The design should account for examiners possibly using a tablet or laptop during live exams, so elements should be large enough and clearly labeled for quick interaction.)_

### Student Flow

**Goal**: Book an assessment time slot and later view exam results.
**Context**: Performed by a student in a course that requires an oral exam (individual or group).

In the student flow, the user logs into OAS and progresses from scheduling their exam slot to eventually viewing their results. The student first sees their assessment details (including any assigned group members) on their dashboard after login. They then navigate to the booking interface to choose from the available time slots (which are validated to have examiners and capacity). Upon booking a slot, the system sends a confirmation and the student can view their scheduled time. On the exam day, the student attends the oral assessment as scheduled, and later (once results are released) they log back in to see their grade and feedback on the platform.

_Figure: Student user flow from login to results. The student finds an available slot, books it, and after the exam can view their feedback in OAS._

1.  **Log In**: The student logs into the OAS web platform using their university credentials (or after receiving a registration email to set up their account, for first-time users). If it's the first login, the student accepts the privacy policy and sets up any profile info required.
2.  **View Assessment Details**: After login, the student's dashboard shows their courses or directly the upcoming oral assessment info. For example, it might display "Oral Exam for Course X - not yet scheduled" with a prompt to book a slot. The student can click into the assessment to see details such as the exam window (dates), instructions, their group members (if it's a group assessment), and the duration of each session.
3.  **Choose a Time Slot**: The student clicks on "Book a Time Slot" which opens the scheduling interface. Here they see a list or calendar of all available slots (dates/times and locations) that still have capacity. Slots may be marked as "Open" (with number of spots left) or "Full". The student can filter by day or time if needed to find a suitable slot. If the assessment is group-based, either one group member is tasked with booking for the whole group or the system ensures that when one member books, it reserves the slot for all members of that group.
4.  **Book Slot**: The student selects a preferred slot and clicks "Book". A confirmation dialog might pop up to verify their choice (especially if it's a group exam, it might warn "You are booking this time for all group members"). The student confirms, and the system reserves that slot for the student (and their group, if applicable). That slot now might disappear for other group members or show as booked to others. The system sends an email confirmation to the student with the details (date, time, venue) and possibly calendar invite. The interface also now shows the booked slot details on the student's view (e.g., "Your exam is scheduled for Oct 10 at 10:00 in Room 5").
5.  **(Optional) Reschedule/Cancel**: If the Course Admin has allowed self-rescheduling, the student might see an option to cancel or change their booking up until a certain deadline. In that case, they would click "Reschedule" and then pick a different slot (the system first frees their current slot, then lets them book a new one). This action would also trigger a new confirmation email. If rescheduling is not allowed or the deadline passed, this option would be disabled and the student must contact an admin to make changes.
6.  **Attend the Assessment**: The student attends the oral exam at the scheduled time and venue (outside the system - this is the real-world exam event). OAS doesn't handle video or online exam conduct (since live video is out of scope), so the student simply goes to the location to meet the examiners. The system doesn't require any action from the student during the exam; however, the examiner might have a device to record marks.
7.  **Result Notification**: After the exam period, once the Course Admin releases results, the student receives an email saying "Your results for Course X Oral Exam are now available." The student then logs back into OAS.
8.  **View Results**: On the student's dashboard or under the specific course assessment page, they can now see their marks and feedback. For individual assessments, it will show their score for each criterion and any comments the examiner(s) provided. For group assessments, they might see a group score and any individual adjustments or individual comments if applicable. The interface should format feedback in a student-friendly way, perhaps summarizing strengths and areas for improvement. Students can only see their own results. They might have an option to download or print their feedback.
9.  **Log Out**: After reviewing feedback, the student logs out. They might also use this opportunity to provide any required acknowledgments (though not specifically in scope, some systems allow students to acknowledge or appeal results - not included here unless added later).

_(Throughout the student flow, the interface should be clean and simple, guiding the student step by step. For instance, after logging in, a prominent call-to-action to "Book your oral exam slot" should be visible to avoid confusion. When no action is needed (e.g., after booking and before results), the UI can reassure the student of their scheduled time and next steps.)_

## Interface Requirements

The OAS user interface and experience should align with modern UX best practices - emphasizing clarity, consistency, and ease of navigation. This section outlines UI/UX design requirements and suggestions for each main user interface component, ensuring the design supports the functional needs described above.

### General Design Principles

- **Web Application Layout**: OAS is a responsive web app (optimized for desktop use, with tablet/mobile-friendly responsive design). Use a clean layout with a top navigation bar or sidebar for switching between major sections (Dashboard, Courses, Scheduling, etc.). Keep the interface uncluttered; only show controls that the user needs for their current task.
- **Branding & Aesthetics**: Follow the university or institution's branding guidelines (colors, logo) to provide a familiar context. Use a consistent design language (for example, Material Design or Atlassian's design system) to ensure a cohesive look and feel across all pages. Typography and color usage should prioritize readability and accessibility (high contrast, legible font sizes).
- **Navigation & Dashboards**: After login, users should see a dashboard tailored to their role:
  - **Students**: Simple dashboard showing their upcoming assessments and any actions required (e.g., "Book your slot").
  - **Examiners**: Dashboard showing a summary of courses/assessments they're involved in and any pending tasks (e.g., "2 slots need examiners" or "5 sessions to mark").
  - **Course Admins**: Dashboard with their courses and a quick status overview (e.g., how many students booked, how many slots have examiners, etc.). Possibly include quick links to create a new course or configure an assessment.
  - **Super Admins**: Minimal dashboard focusing on pending admin approvals and a count of courses/system usage.
    A clear menu or toggle to switch context (for users with multiple roles, though typically roles don't overlap except Super Admin who might also be a Course Admin for a course).
- **Consistency**: Common interface elements (buttons, form fields, tables) should behave uniformly across the app. For instance, all forms for data input (CSV upload, create assignment, etc.) should have consistent styling and validation feedback. Primary actions (like "Save", "Submit", "Cancel") should be placed and colored consistently to train user expectations.

### Super Admin Interface

Super Admins have a limited but important interface focused on user management:

- **Access Management Screen**: A page listing all pending Course Admin access requests with an "Approve" or "Reject" action for each. Approvals could open a modal for confirmation. After approving, the new Course Admin receives an email. If no pending requests, this page can indicate "No pending admin requests."
- **All-Courses Overview**: A read-only listing of all courses in the system. This could be a table with columns (Course Name, Course Code, Semester/Term, Course Admin Name). Super Admins can search or filter this list. This view provides assurance of what's in the system without exposing any sensitive data (no student info here).
- **Navigation**: Super Admins should have a simple navigation - likely just two primary options: "Manage Admins" and "View Courses". Perhaps these can be tabs on a single page.
- **Style**: Use the same core UI components as other parts of the app. Since content is mostly tables and lists, ensure they are sortable and scalable. Also include feedback messages e.g., "Course Admin approved successfully" - after actions.

### Course Admin Interface

Course Admins require a robust interface as they perform the most configuration. Key UI components and considerations:

- **Course Selection**: If a Course Admin manages multiple courses, they need an easy way to switch between them. This could be a dropdown of courses or a "My Courses" page that lists each course as a card or row to click into. Once a course is selected, the interface context switches to that course's data.
- **Course Dashboard**: Inside a course, provide an overview page summarizing the course's assessments. For example, tiles or a list for each Assignment (Assessment) with status info (e.g., "Oral Exam 1-20 students, 5 groups, Booking open, Results not released"). A prominent button "Create New Assessment" should be available here.
- **Assessment Configuration Wizard**: Creating or editing an assessment (assignment) could be implemented as a multi-step wizard or as a single page with tabs/sections. A recommended approach is a step-by-step wizard to guide Course Admins through the required configuration in logical order (this reduces cognitive load and ensures nothing is missed). For example:
  - **Basics**: Assignment name, description, type (Individual/Group/Mixed).
  - **Participants**: Upload CSV of students/groups. After upload, display the list of participants and groups, allowing the admin to verify or edit minor details (if needed).
  - **Rubric**: Launch the Rubric Builder UI. This might be an embedded section or a dedicated modal/page because it's a complex task. The Rubric builder should allow adding criteria. For each criterion, the admin can click "Add Level" to create a performance level. Consider a small inline form or modal for entering level name and points. The UI should also show a field or link to "Manage Comments" for each criterion, where the admin can enter predefined comments. To avoid clutter, clicking "Manage Comments" might open a sub-dialog listing existing comments and an option to add new ones. Once the rubric is saved, perhaps show a summary (like a table of criteria and levels) on the main wizard page.
  - **Scheduling**: The interface for defining time slots can use a table format where each row is a slot. Provide inputs for date, start time, end time (or duration calculation), venue, # of examiners required, # of sessions in that slot. The admin can add multiple rows. For convenience, include a "Add multiple slots" tool - e.g., the admin might specify a date range or multiple days and a template (like "every 15 minutes from 9:00 to 11:00") to auto-generate slots. The UI should visually group slots by date (for clarity) and indicate if any overlap in time (if that's not allowed). If parallel slots (same time, different venue) exist, they can be shown side by side or with a label. Validation: warn the admin if two slots share the same examiner requirement and time (overlap) unless intended.
  - **Examiners**: A screen to assign examiners to the course/assignment. Likely this lists all users with examiner role currently added. The admin can click "Add Examiner" to invite a new examiner (enter email/name, etc.) or select existing ones from a list. Next to each examiner's name, show how many sessions they are assigned to (initially 0) and the limit set for them. The admin sets a global session limit (or individual limits) here. It might be simplest to set one limit that applies to all examiners for fairness.
  - **Review & Publish**: A final review step showing a summary of all settings (perhaps a checklist: "Students uploaded: X; Rubric: 5 criteria; Slots: Y slots from Date A to Date B; Examiners added: N"). If everything looks good, the admin clicks "Confirm & Publish" (or "Save Configuration"). This makes the assessment active. Students and examiners might then be notified if configured to do so.
    Throughout the wizard, provide "Back" and "Next" navigation, and allow saving progress at any point (in case the admin wants to finish configuration later). Also allow canceling (with confirmation) if the admin wants to discard changes.
- **Managing Live Assessment**: Once an assessment is published, the Course Admin interface for that assessment could switch to a management mode. This includes:
  - **Overview Dashboard**: As mentioned, showing key stats (e.g., how many slots defined, how many examiners signed up, how many students booked, any invalid slots).
  - **Edit/Update Configurations**: The admin can still update certain things if needed - e.g., add another time slot, or adjust the rubric (though ideally rubric changes should be locked once marking starts). The UI should inform what can/can't be changed after publishing. For example, "You can still add slots or adjust examiner limits, but cannot change rubric once exams have begun."
  - **Booking Management**: A view of all time slots and which student/group is booked in each. The admin should be able to manually move a booking here (drag-and-drop a student from one slot to another, for instance) if necessary, or book a student who hasn't self-booked.
  - **Real-time Monitoring**: Possibly a visual indication on the schedule of which slots are currently in progress (if the current time is within a slot and it's booked, highlight it) and which examiner is in each. This could help the admin locate issues (like an examiner running behind schedule).
- **Reports**: The Course Admin interface should have a section or tabs for the three key reports (Scheduling Overview, Mark Results, Examiner Trends). These can be tables or charts:
  - **Scheduling Overview Report**: Likely a table with one row per time slot, showing slot details (time, venue), examiner(s) assigned, student booked, and a status (valid/invalid). This helps identify if more examiners are needed for any slot.
  - **Mark Results Report**: A table or matrix where rows might be students and columns might be criteria, but since multiple examiners and comments are involved, this could be a drill-down interface. One approach: a list of students/groups; clicking one expands to show the marks each examiner gave for each criterion and the comments. Alternatively, have criteria as rows and examiners as columns for that student - but this might be complex. The UI should at least allow the admin to see if two examiners diverged greatly on a score. Also include controls for selecting the aggregation method (perhaps a dropdown at top: "Aggregation method: [Average]") which then recalculates the aggregated marks.
  - **Examiner Trends Report**: Perhaps a simple table: each examiner's name and their average score given (per criterion or overall). Possibly visualize this with a bar chart. This data updates as marking progresses, giving the admin insight into consistency.
    Each report page should have an export button to download the data.
- **Result Release**: The UI must include a control to release results to students when ready. This could be a button on the overview or results report page, labeled "Release Results to Students". It should prompt confirmation ("Are you sure you want to release scores to students? This action will notify 20 students."). Once done, the status of the assessment changes to "Results Released" and students can see their feedback.
- **Feedback for Actions**: All major actions the admin takes (publishing an assessment, adding a slot, releasing results, etc.) should prompt success messages or error messages if something goes wrong. For example, if a CSV upload fails validation, the UI should display an error highlighting what's wrong (e.g., "Error on line 23: missing student ID").
- **Overall UX**: The Course Admin interface deals with potentially complex data, so use progressive disclosure: don't show all details at once, but allow the admin to drill down. For instance, show a summary of a rubric criterion, but clicking it can expand to show all performance levels and comments. Use modals or separate pages for intensive tasks like building a rubric or viewing detailed reports, so as not to overwhelm the main screen.

### Examiner Interface

Examiners primarily interact with scheduling and marking interfaces, so their UI should be optimized for those tasks:

- **Examiner Dashboard**: A page that lists the assignments or courses the examiner is involved in. For each assignment, show any actions needed: e.g., "You have not signed up for slots" or "5 sessions assigned to you". This helps examiners quickly know what to do first.
- **Available Slots View**: A core screen where examiners see all time slots for an assignment. This could be a table with slots as rows and key info in columns (Date/Time, Venue, Students (if booked), Examiners needed vs assigned). Slots that still need examiners could be highlighted. Each slot might have a button "Sign up" or "Join" for examiners to click. If an examiner has already joined a slot, indicate that (e.g., a checkmark or "You are assigned"). Possibly provide a calendar-style view as well, but a simple list grouped by day might suffice since examiners will focus on filling needed slots.
- **Personal Schedule**: Once examiners have assigned themselves, they need a schedule view. This could be a consolidated list of all upcoming sessions they will examine. Include date, time, venue, and which student or group is scheduled (if known at that time). This page should be printable or at least easily viewable on a mobile device, as examiners might carry it with them. If changes occur (like a student reschedules to a slot the examiner was covering), the examiner's schedule updates and possibly a notification is sent.
- **Marking Interface**: This is the most critical part of the examiner UI and should be designed for efficiency and clarity:
  - Present the student or group name at top, along with slot info (date/time, perhaps the examiners' names for reference). If it's a group exam, list all group members' names.
  - Display the rubric in a structured way. One common design is a table: criteria in rows, levels in columns (like a matrix). However, with variable levels per criterion, a simpler approach is to list each criterion as a section:
    - Each criterion shows its description, the maximum points, and then a set of radio buttons or a dropdown list for the performance levels. For example, criterion "Communication" might have a dropdown with options: Excellent (5 pts), Good (4 pts), Fair (3 pts), Poor (2 pts). The examiner selects one.
    - Next to that, a text box or icon for predefined comments. Possibly an icon (💬) that opens a list of preset comments; clicking a comment adds it to the comment field. The examiner can edit or append text as needed.
    - If the examiner wants to add a completely new comment to the library, an "Add to library" checkbox or button could appear when they type a comment that isn't preset, allowing them to save it for future use.
  - Do this for each criterion. Criteria might be collapsible sections if there are many, but ideally keep them all visible to reduce clicking. If an examiner needs to mark multiple students in a group: one UI idea is to have a tab for each student for the individual portion. Another idea (as the client suggested) is a single page listing each student's name under each criterion to directly enter individual scores in one view. This second approach is more complex to design, so the team should evaluate if it's feasible without clutter. Perhaps if there are few criteria, listing students across might work; if there are many criteria, tabs might be cleaner.
  - **Overall feedback**: a large text area at the bottom for overall session feedback (if applicable).
  - **Notes**: a separate text area labeled "Notes (visible to admin only)" to distinguish it from feedback to student. This field should be visually distinct (perhaps a different color background) to remind examiners it's not shared with the student.
  - **Save/Submit Controls**: At the bottom or top, provide buttons for "Save Draft" and "Submit Final". The UI should make it clear whether the current state is saved or not (e.g., "Last saved 5 minutes ago" if auto-save is implemented, which would be nice to have during marking). After clicking "Submit Final", ask for confirmation ("Once submitted, you cannot edit marks unless unlocked by an admin"). After submission, lock the fields and indicate "Submitted".
  - Possibly include a navigation element if the examiner wants to jump to another student's marking form directly from this screen (for efficiency if they are doing multiple in one sitting e.g., a "Next student" button if the examiner knows the next session is starting).
- **Usability Considerations**: The examiner interface should be tested for scenarios where an examiner might need to operate quickly. For example, keyboard shortcuts or quick-select for rubric levels (like using arrow keys to change level selection) can save time. Also, ensure the interface works offline or has fail-safes (though not an explicit requirement, consider autosave in case of connection issues).
- **Responsive Design**: Examiners might bring a tablet into the exam room. The marking interface should adapt to a tablet screen (e.g., using responsive design to stack elements vertically if needed). Large touch targets for dropdowns and buttons will help tablet use.

### Student Interface

The student-facing interface is focused on simplicity and guiding the student to take the necessary actions (booking and viewing results):

- **Student Dashboard**: After login, a student sees an overview of any assessments that concern them. Likely, it will list their courses and any active assignments requiring action. For an oral exam that needs scheduling, the dashboard (or course page) should prominently show a message like "Oral Assessment Scheduled: Not booked Book your time slot now." If the student already booked, it would show "Scheduled on [Date] at [Time], [Venue]" with perhaps an option to change it (if allowed). If results are released, it might show a summary of "Result: [Grade] View feedback". Essentially, this dashboard/card needs to cover three states: not booked yet, booked, and results available.
- **Booking Page**: When the student clicks to book, present a clear interface for selecting a slot:
  - A simple list of slots sorted by date/time is one approach, with a "Book" button next to each available slot. Or a calendar view where the student picks a day then sees slots. Given simplicity, a list grouped by day might be best. Each slot entry shows the time range and location. If group booking is required, indicate if the slot is for the whole group ("1 slot per group") so students understand only one should book. Possibly show how many seats left ("2 spots left" if multiple individuals can book the same slot, though in this scenario it's typically one group or one individual per slot).
  - When the student clicks "Book" on a slot, show a confirmation dialog summarizing the selection. Upon confirmation, provide immediate feedback on the page (e.g., "You have booked [Date Time] at [Venue]"). Remove or disable that slot from the list to prevent double booking. If group, also show group members a message that the group is booked.
  - If rescheduling is allowed, the student would come back to this page and see an option "Cancel booking" or "Change booking" which then re-enables the list of slots. Use warnings like "Are you sure you want to change your booking? Your current slot will be freed for others."
- **Confirmation & Reminders**: After booking, the interface should display the booked slot details clearly. For example, on the course page: "Your oral exam is booked for: June 10, 2025 at 10:00 AM in Room 101." Also mention "You will receive an email confirmation and a reminder 1 day before the exam." This sets expectations. If anything changes (admin changes a venue or time), the system should notify the student via email; the UI should always reflect the current correct details.
- **Group Information**: If applicable, provide a way for students to see their group members and perhaps their contact info (email) so they can coordinate, especially for group assessments. This could be a simple list on the assessment page: "Your Group: You + [Student B] + [Student C]". This helps the group decide who will book the slot and ensures everyone knows they're in the same boat.
- **Results Page**: Once results are released, the student should be able to view their performance in a clear, jargon-free format. On the assessment page (or a dedicated Results page for that assessment), show:
  - Their overall score (e.g., "Final Score: 85/100") if that concept exists. Possibly also their rank or grade if the course uses that, but likely not needed here.
  - Breakdown by criterion: a list of each rubric criterion with the level they achieved or points, and any comments for that criterion. For example:
    - Communication: Good (4/5) - "Spoke clearly but needed more concise answers."
    - Technical Knowledge: Excellent (5/5) - "Demonstrated thorough understanding of all concepts."
      and so on.
  - Overall comments: any general feedback from the examiners about their performance.
  - If multiple examiners gave input, the comments may be combined or attributed. The system might consolidate comments per criterion (if multiple examiners each gave one, perhaps they are listed or merged). The PRD doesn't require exposing multiple examiner identities to students, so likely students just see the combined result.
  - Make this page printable or savable (students may want to keep a copy of feedback). A "Download PDF of Feedback" button could be useful.
- **Ease of Use**: The student's usage of OAS should require little to no training. Use straightforward language ("Book a time" instead of "schedule slot") and guide them if, for example, an assignment isn't open for booking yet ("The booking window will open on May 1st. Please come back then."). If something is not applicable, hide it - e.g., if a student is in an individual assessment, they don't need to see any group-related UI.
- **Accessibility & Support**: Ensure that all interactive elements for students (like the slot booking list) are accessible via keyboard and screen-reader friendly (slots should be properly labeled with dates etc.). Provide help text or a FAQ link if the process might be confusing (e.g., "How do group bookings work?" could be a small info icon that explains it).

### Additional Interface Considerations

- **Error Handling**: The UI should handle error cases gracefully. For instance, if a student's booking action fails because the slot just got taken by someone else, show an informative message and refresh the slot list. Similarly, if an examiner tries to sign up for a slot but they've hit their limit, explain "You have already signed up for the maximum number of sessions allowed." Clarity in error messages is key.
- **Session Timeout & Saving**: For security, sessions might auto-logout after some inactivity. Warn users (especially examiners and admins in the middle of work) and auto-save any in-progress data.
- **Audit Trail (Admin UI)**: Although an internal detail, having an interface for admins to view logs of critical actions (e.g., who changed what) might be beneficial. This could be as simple as listing recent actions on the course dashboard for admins ("Today 10:00 - Examiner X submitted marks for Student Y"). This is not a core requirement, but a nice-to-have for transparency.

By adhering to these interface requirements, OAS will provide a user-friendly experience for all roles. The design takes cues from well-established patterns in modern web applications, ensuring users can intuitively navigate and accomplish their goals without confusion. The focus on role-specific dashboards, guided workflows, and clear visual cues will help minimize training and support needed for the platform.

## Out of Scope

For clarity, the following items are not included in the OAS design and functionality, as agreed in the project scope:

- **Direct University System Integration**: OAS will not directly integrate via live APIs with existing university databases or authentication systems. There is no Single Sign-On (SSO) with the university's login; users will log in with OAS-specific credentials (or links from Canvas). Data exchange with the LMS is done via CSV import/export, not real-time syncing 4.
- **Native Mobile Application**: The project will deliver a responsive web application only. No separate mobile app (iOS/Android) will be developed. Users can access the web interface on mobile browsers, but there is no plan for a platform-specific app.
- **Advanced Analytics & AI Insights**: Beyond the reporting described, there will be no advanced analytics dashboards or data science features in this phase. For example, no AI-driven analysis of examiner grading patterns or predictive analytics on student performance is included. Likewise, there's no automated grading or AI-assisted scoring of students' answers - all grading is manual by human examiners.
- **Live Video or Online Proctoring**: OAS does not include any video conferencing or live online assessment capabilities. It assumes in-person oral exams (or if remote, the institution would use a separate tool like Zoom/Teams for the call). There's no feature for recording sessions or streaming video in this system.
- **Payment Processing or External Scheduling APIs**: (Not mentioned above but implied) If the university charges fees or uses external booking APIs (like Calendly/Cal.com), those are not integrated. The scheduling system is custom and internal.
- **Other Non-Essential Features**: Any features not outlined in this PRD, even if potentially useful, are out of scope. For example, no functionality for students to upload preparation materials, no peer feedback mechanisms, and no multi-language support (unless the system default language is English only, additional languages are out of scope initially). These can be considered for future enhancements but are not in the current requirements.
