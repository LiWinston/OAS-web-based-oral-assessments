# OAS 口语评估 · 学生预约与场次管理

## 目的与范围
本文详细描述学生预约的生命周期与场次管理机制，覆盖 INDIVIDUAL（个人）、GROUP（小组）、MIX（混合）三种作业类型。重点阐述时段到场次的生成算法、考官配岗的硬性约束（Gatekeeper）以及预约状态机的流转逻辑。

## 核心概念辨析
- **时段（TimeSlot）**：管理员配置的大时间窗口（如 09:00-12:00），是生成场次的“模具”。包含单场时长（Duration）和场间休息（Gap）。
- **场次（SlotSession）**：实际的考试单元（如 09:00-09:15, 09:20-09:35）。它是学生预约和考官评分的实体载体，拥有独立的容量（Capacity）和 ID。
- **配岗（Staffing）**：将考官（SysExaminer）分配给具体场次的过程。这是发布成绩的前提条件。

## 1. 场次生成与管理（Admin Side）
### 1.1 自动切分算法
系统不要求管理员手动创建成百上千个场次，而是采用“时窗切分”策略：
- **输入**：`startTime`, `endTime`, `sessionDuration`, `breakDuration`。
- **逻辑**：从 `startTime` 开始，循环计算 `end = start + duration`。若 `end <= endTime`，则生成一个 `SlotSession`，并步进 `start = end + gap`。
- **资源冲突**：生成时会检查 `Venue`（场地）在目标时间段是否已被占用，确保物理资源互斥。

### 1.2 考官配岗与限制
- **批量复制**：支持将一个场次的考官配置“复制”到同一时段下的所有场次，大幅降低操作成本。
- **负载均衡**：系统维护 `ExaminerAssignmentLimit` 表，校验考官的总工作时长或场次数量，防止疲劳排班。

### 1.3 发布门禁（Release Gatekeeper）
- **规则**：作业发布给学生（`RELEASED_TO_STUDENTS`）是一个不可逆且严肃的操作。
- **约束**：系统强制检查**所有**场次是否都已分配了足够数量的考官。
- **目的**：防止学生预约了场次却发现没有考官，导致考试无法进行的教学事故。若存在未配岗场次，发布操作将直接失败并返回具体错误。

## 2. 学生预约生命周期（Student Side）
### 2.1 预约状态机
预约记录（`SessionStudent`）的生命周期如下：
1.  **Created**：学生发起预约，扣减场次容量成功。
2.  **Rescheduled**：学生改约到新场次（旧记录删除/标记失效，新记录创建，旧容量释放，新容量扣减）。
3.  **Cancelled**：学生取消预约（记录删除，容量释放）。
4.  **Completed**：考官提交了评分（Assessment Submitted）。

### 2.2 核心校验逻辑
- **容量校验（Capacity Check）**：利用数据库乐观锁（`capacity > 0`）防止超卖。
- **重复校验（Duplicate Check）**：同一学生在同一作业下只能有一个有效预约。
- **冲突校验（Conflict Check）**：检查学生在目标时间段是否已有其他作业的考试（跨作业冲突）。
- **锁定校验（Lock Check）**：一旦考官已保存草稿或提交评分，学生**禁止**取消或改约，防止成绩数据悬空。

### 2.3 不同作业类型的适配
- **INDIVIDUAL**：标准的一人一场。
- **GROUP**：
  - 组长代表小组预约，或组员单独预约（视业务配置）。
  - 预约成功后，该场次容量扣减 1（通常一个小组占一个 Slot）。
  - 系统会校验小组成员的资格。
- **MIX**：逻辑同 GROUP，但后续评分阶段会分裂为个人和小组两部分。

## 3. 关键表结构与交互
- `assignment`：定义作业类型与发布状态。
- `time_slot`：定义生成规则。
- `slot_sessions`：核心实体，存储 `capacity`（剩余容量）和 `max_capacity`。
- `session_student`：关联表，记录 `student_id` 与 `session_id`。
- `session_examiners`：关联表，记录 `examiner_id` 与 `session_id`。
