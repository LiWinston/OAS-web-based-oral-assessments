# OAS 口语评估 · 学生成绩与反馈接口

## 1. 核心设计思想：读写分离与协商缓存
本模块主要服务于学生端的高频查询请求。与管理端不同，学生端的特点是 **读多写少**（成绩发布后基本不变）且 **并发集中**（成绩发布通知发出后会有瞬时流量高峰）。因此，设计重点在于 **缓存机制** 和 **数据聚合效率**。

### 1.1 HTTP 协商缓存 (Negotiation Caching)
为了减轻服务器带宽压力并提升移动端体验，我们在成绩详情接口实现了标准的 HTTP 协商缓存机制。

*   **机制**: 利用 `Last-Modified` 和 `If-Modified-Since` 请求头。
*   **流程**:
    1.  **首次请求**: 客户端请求成绩，服务器返回数据，并在 Header 中带上 `Last-Modified: <发布时间>`。
    2.  **后续请求**: 客户端再次发起请求时，Header 中带上 `If-Modified-Since: <上次的发布时间>`。
    3.  **服务端校验**: 检查数据库中该成绩的 `updated_time` 或 `release_time`。
        *   如果未变更: 直接返回 **304 Not Modified**，Body 为空。客户端直接使用本地缓存。
        *   如果已变更: 返回 **200 OK** 和新的数据 Body。
*   **收益**: 在成绩未更新的情况下，网络传输量减少 99%（仅传输 Header），极大降低了数据库查询压力（如果配合 Redis 缓存 Last-Modified 时间）。

### 1.2 数据聚合与 DTO 投影
学生端的成绩展示需要聚合多张表的数据：`Assessment`（分数）、`Rubric`（量规详情）、`Booking`（场次信息）、`Feedback`（文本评价）。

*   **MyBatis 关联查询**: 我们没有使用 JPA 的懒加载（N+1 问题风险），而是使用 MyBatis 的 `<resultMap>` 进行级联查询，或者在 Service 层进行并行查询组装。
*   **DTO 设计**:
    *   `StudentResultOverviewDTO`: 列表页使用，仅包含总分、等级、发布状态等轻量字段。
    *   `StudentResultDetailDTO`: 详情页使用，包含完整的量规打分矩阵（Rubric Matrix）和富文本反馈。

## 2. 安全性设计：IDOR 防护
学生只能查看 **自己** 的成绩。这是一个典型的 **IDOR (Insecure Direct Object Reference)** 漏洞高发区。

*   **防护逻辑**:
    *   接口路径虽然是 `/api/students/{studentId}/results`，但我们在拦截器或 Service 层会强制校验：`Current_User.id == path_variable.studentId`。
    *   如果当前登录用户是学生，且尝试访问其他 ID 的数据，直接抛出 `403 Forbidden`。
    *   对于管理员，则放行此校验（RBAC 权限控制）。

## 3. 业务流程与状态机

### 3.1 成绩发布流程
成绩并非打分后立即可见，需经过“发布”动作。
1.  **Draft (草稿)**: 考官正在打分，学生不可见。
2.  **Committed (已提交)**: 考官提交，等待管理员审核/发布。
3.  **Released (已发布)**: 管理员点击“发布”，此时 `release_time` 被设置，学生端可见。

### 3.2 隐私保护
*   **匿名化**: 在某些敏感的反馈展示中（如小组互评），系统会自动隐藏评价者的姓名，仅显示“Peer Reviewer”。
*   **数据脱敏**: 传输给前端的 JSON 中，不包含考官的个人手机号等隐私信息，仅包含 `Examiner Name`。

## 4. 常见问题与面试点
*   **Q: 为什么不直接用 Redis 缓存整个成绩 JSON？**
    *   A: 成绩数据虽然读多写少，但一旦修改（如复核改分）需要实时生效。使用 HTTP 304 缓存是客户端缓存，服务器无状态，成本最低。如果使用 Redis，需要处理缓存失效（Cache Invalidation）的一致性问题。对于目前的并发量，数据库配合索引查询已经足够快，HTTP 缓存主要解决带宽问题。
*   **Q: 如何防止学生通过遍历 ID 爬取全班成绩？**
    *   A: 除了上述的 IDOR 校验（只能查自己），我们还配置了 **Rate Limiting (限流)**。如果同一个 Token 在 1 分钟内请求了超过 50 次成绩接口，会被暂时封禁 IP，防止恶意爬虫。
