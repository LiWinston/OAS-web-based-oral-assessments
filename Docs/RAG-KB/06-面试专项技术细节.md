# OAS 口语评估 · 面试专项技术细节

## 目的与范围
本文档专为技术面试准备，深入解析系统中的关键技术难点、设计模式应用、并发处理方案及架构决策。内容涵盖高并发预约、复杂排课逻辑、MIX 模式双写架构、CSV 管道设计及安全体系。旨在帮助候选人清晰阐述“前因后果”与“设计思想”。

## 1. 高并发下的预约一致性保障（防超卖）
### 1.1 业务背景与挑战
在口语评估场景中，热门时段（如考试周最后几天的晚间场次）往往面临“秒杀”级的并发压力。如果多个学生同时发起预约请求，而系统仅在应用层检查 `capacity > 0`，极易出现“读-写”时间差，导致实际预约人数超过场次容量（超卖）。这不仅引发考场资源冲突，还可能导致严重的教学事故。

### 1.2 技术方案演进
- **方案一：应用层锁（Synchronized/ReentrantLock）**
  - *缺陷*：仅适用于单机部署。一旦后端服务扩展为多实例集群，JVM 级别的锁失效，无法保证跨节点的互斥。
- **方案二：分布式锁（Redis Redlock）**
  - *缺陷*：引入了额外的组件依赖（Redis）和网络开销。对于当前系统的并发量级（千级 QPS），维护一套高可用的 Redis 锁机制成本过高。
- **最终方案：数据库乐观锁（CAS 变体）**
  - *核心思想*：利用数据库自身的行级锁（Row Lock）原子性，将“检查”与“扣减”合并为一条 SQL。
  - *实现细节*：
    ```sql
    UPDATE slot_sessions 
    SET capacity = capacity - 1 
    WHERE id = #{sessionId} AND capacity > 0
    ```
  - *执行逻辑*：这条 SQL 会返回受影响的行数。
    - 若返回 `1`：表示扣减成功，事务继续提交。
    - 若返回 `0`：表示库存不足（`capacity > 0` 条件不满足），业务层直接抛出 `CapacityFullException`，触发事务回滚。
  - *优势*：零外部依赖，强一致性保障，且在 MySQL InnoDB 引擎下性能表现优异，完美契合当前架构。

## 2. 复杂排课算法与不可变护栏
### 2.1 时窗切分算法
排课不仅仅是简单的循环，需要处理复杂的边界条件。
- **算法逻辑**：
  1.  **输入**：大时段窗口（TimeSlot，如 09:00-12:00）、单场考试时长（Duration，如 15min）、场间休息（Gap，如 5min）。
  2.  **滑动窗口**：从 `startTime` 开始，计算 `currentEnd = currentStart + duration`。
  3.  **边界校验**：若 `currentEnd <= endTime`，则生成一个有效场次（Session）。
  4.  **步进**：`nextStart = currentEnd + gap`。
- **资源冲突检测**：在生成过程中，系统会实时查询 `Venue` 表，检查同一物理场地在目标时间段内是否已被其他作业占用，确保物理资源的唯一性。

### 2.2 不可变护栏（Immutability Guardrail）
- **设计思想**：为了防止“正在进行的考试被修改”这一灾难性场景，系统引入了状态机护栏。
- **实现机制**：
  - 在所有涉及排课修改（增删改场次、修改考官）的接口中，植入前置拦截器或切面。
  - 检查 `Assignment` 的状态。一旦状态流转为 `RELEASED_TO_STUDENTS`（已发布给学生），系统即认为该时间表已成为“公共契约”。
  - 任何试图修改已发布场次的操作都会被立即拒绝（抛出 `IllegalStateException`），强制要求管理员先撤回发布（Unpublish），从而确保数据变更的显性化和安全性。

## 3. MIX 模式的双写与聚合架构
### 3.1 业务难点：小组与个人的二象性
混合模式（Mixed Mode）是本系统的核心业务难点。一个小组的评分（Group Submission）既是独立的实体，又必须实时映射到组内每个成员的个人成绩单（Individual Submission）。
- **挑战**：考官通常只给小组打一个总分，但系统需要支持对个别表现突出的学生进行“微调”。这就要求数据既要“联动”，又要“独立”。

### 3.2 架构设计：主从联动与自动扇出
- **主从模型（Master-Slave）**：
  - **Master**：小组提交记录（AssessmentSubmission where type='GROUP'）。
  - **Slave**：组内成员的个人提交记录（AssessmentSubmission where type='INDIVIDUAL'）。
- **自动扇出（Fan-out）机制**：
  - 当考官提交小组评分时，`AssessmentServiceImpl` 会触发联动逻辑。
  - 系统查询该组的所有成员，遍历为每个人创建或更新个人评分记录。
  - **关键逻辑**：将小组的得分（经过权重计算后）自动填充到个人的“小组分”字段中，同时保留个人已有的“个人分”字段。
- **事务一致性**：
  - 整个扇出过程包裹在 `@Transactional` 注解中。这意味着“保存小组分”和“更新5个学生的个人分”是一个原子操作。要么全部成功，要么全部回滚，坚决杜绝“小组有分，学生没分”的数据不一致状态。

## 4. Canvas 兼容的 CSV 管道设计
### 4.1 设计模式：策略工厂（Strategy & Factory）
- **问题**：系统需要处理学生、小组、考官、混合等多种类型的 CSV 导入导出，且每种类型的表头校验、解析逻辑各不相同。
- **解决方案**：
  - 定义 `CsvHandler<T>` 泛型接口，包含 `import`、`export`、`validateHeader` 等方法。
  - 实现 `StudentCsvHandler`、`GroupCsvHandler` 等具体策略类。
  - 构建 `CsvHandlerFactory`，利用 Spring 的 `ApplicationContext` 或 Map 注册机制，根据前端传入的 `type` 参数动态分派处理器，符合开闭原则（OCP）。
- **收益**：符合开闭原则（OCP）。新增一种导入类型（如“助教导入”）时，只需新增一个 Handler 类，无需修改 Controller 核心逻辑。

### 4.2 健壮性与流式处理
- **抗噪设计**：Canvas 导出的 CSV 常带有 BOM 头（Byte Order Mark）或表头空格。Handler 内部实现了自动清洗逻辑，通过 `BOMInputStream` 去除头部字节，并对表头进行 `trim()` 处理，极大降低了用户的挫败感。
- **ZIP 流式打包**：
  - 在导出 Mixed 作业时，需要同时提供“个人”和“小组”两份 CSV。
  - 系统没有选择生成两个临时文件再打包，而是使用了 `ZipOutputStream` 包装 `ByteArrayOutputStream`。
  - 数据在内存中直接被渲染为 CSV 格式并写入 ZIP 条目（Entry），最终以流的形式直接写回 HTTP 响应。这种“零落盘”设计显著减少了磁盘 I/O 开销和临时文件清理的负担。

## 5. 安全体系：双 Token 机制与过滤器链
### 5.1 双 Token 机制（Access + Refresh）
- **设计考量**：为了平衡安全性（短效 Token 减少泄露风险）与用户体验（长效登录避免频繁输入密码）。
- **机制详解**：
  - **Access Token**：有效期短（如 15 分钟），用于日常接口请求，无状态，载荷包含用户 ID 和角色。
  - **Refresh Token**：有效期长（如 7 天），存储在数据库 `sys_refresh_token` 表中。
  - **刷新流程**：当 Access Token 过期，前端调用 `/token/refresh` 接口，携带 Refresh Token。后端校验数据库中该 Token 是否存在且未过期/未撤销，验证通过后签发新的 Access Token。
  - **安全增强**：
    - **撤销机制**：用户登出或修改密码时，系统会调用 `revokeAllByUserId` 标记数据库中的 Refresh Token 为“已撤销”。这解决了传统 JWT 无法服务端强制登出的痛点。
    - **轮转策略**：每次刷新时，旧的 Refresh Token 也可以被设计为失效（可选），进一步提升安全性。

### 5.2 自定义过滤器链
Spring Security 默认过滤器无法满足特定需求，因此扩展了 Filter Chain：
1.  **XssFilter**：
    - 包装 `HttpServletRequest` 为 `XssHttpServletRequestWrapper`。
    - 重写 `getParameter` 等方法，使用 HTML 转义库清洗输入，从源头防止存储型 XSS 攻击。
2.  **RepeatableFilter**：
    - 防止表单重复提交。
    - 拦截写请求，计算请求特征值（Token + URL + 参数摘要）。
    - 将特征值存入缓存（如 Redis 或本地 Cache）并设置短过期时间（如 5 秒）。若相同特征值再次出现，直接拦截。

## 6. 性能优化：协商缓存与异步解耦
### 6.1 HTTP 协商缓存（If-Modified-Since）
- **场景**：学生频繁刷新成绩页面，但成绩一旦发布很少变更。
- **实现**：
  - 客户端请求携带 `If-Modified-Since` 头（上次获取的时间戳）。
  - 服务端（`StudentResultsController`）查询数据时，对比数据的 `update_time`。
  - 若 `update_time <= If-Modified-Since`，直接返回 `304 Not Modified` 状态码，不返回响应体。
- **收益**：将网络传输量从 KB 级降低到 0，显著提升移动端弱网环境下的加载速度，同时降低服务器序列化 JSON 的 CPU 开销。

### 6.2 异步通知解耦
- **场景**：CSV 导入 500 名学生时，需要发送 500 封激活邮件。若同步发送，接口响应时间将超过 1 分钟，导致前端超时。
- **方案**：
  - 引入 `NotificationQueueService`。
  - 导入接口仅负责将“发送邮件”的任务元数据（收件人、模板、参数）写入数据库或消息队列。
  - 独立的后台线程（或 `@Async` 任务）异步消费队列，执行实际的 SMTP 发送逻辑。
- **收益**：导入接口响应时间降低至毫秒级，且邮件发送失败不会影响导入业务的主流程成功率。
